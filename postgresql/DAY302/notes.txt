Day 302 - Foreign Keys & Referential Integrity

Topic Overview:
Today we linked tables together using FOREIGN KEY constraints. In MongoDB, relationships are either embedded subdocuments or loose `ObjectId` references where the database doesn't care if the referenced document actually exists.
In PostgreSQL, referential integrity is strictly enforced. You cannot insert an order for a `user_id` that doesn't exist in the `users` table!

Delete actions on Foreign Keys:
- ON DELETE RESTRICT (Default): Prevents deleting the parent row if any child rows reference it. Perfect for bank users with transaction history.
- ON DELETE CASCADE: When parent is deleted, all dependent child rows are automatically deleted. Good for things like `cart_items` when a user account is deleted, but dangerous for financial records!
- ON DELETE SET NULL: Sets the foreign key in child rows to NULL when parent is deleted. (Child column must be nullable).
- ON DELETE NO ACTION: Similar to RESTRICT, evaluated at the end of the statement or transaction.

Keep an eye on:
- In production payment systems, almost NEVER use `ON DELETE CASCADE` for orders, invoices, or ledger tables. You want immutable audit trails. If a user deletes their profile, either soft-delete (`is_deleted = TRUE`) or use `RESTRICT` so they can't delete an account with active orders.
- Foreign keys do NOT automatically create an index on the referencing column in PostgreSQL! Always create an explicit index on foreign key columns (`CREATE INDEX idx_orders_user_id ON orders(user_id)`), otherwise table joins will do slow sequential scans.
