Day 312 - Indexes & Performance Tuning

Topic Overview:
Today I learned why some queries run in 1 millisecond while others take 4 seconds: Indexes!
Without an index, PostgreSQL must perform a Sequential Scan (`Seq Scan`) — scanning every single page on disk from top to bottom.
With a B-Tree index, Postgres traverses a balanced tree in O(log n) lookups.

Key Index Types & Tools:
- B-Tree (Default): Great for `=`, `<`, `>`, `<=`, `>=`, and `BETWEEN`.
- Composite Index: Index on multiple columns `(city, created_at DESC)`. Order of columns matters! (Leftmost prefix rule).
- Partial Index: Index only a subset of rows! E.g. `CREATE INDEX idx_pending_orders ON orders(order_id) WHERE status = 'PENDING';`. Saves massive disk space if 99% of your orders are already DELIVERED.
- EXPLAIN: Shows the query execution plan generated by the optimizer.
- EXPLAIN ANALYZE: Actually executes the query and shows real wall-clock timing and buffer usage!

Keep an eye on:
- Do NOT index every single column! Every index slows down INSERT, UPDATE, and DELETE operations because Postgres has to write to both the heap table and the index tree on every write.
- If a table has only 50 rows, Postgres optimizer will deliberately ignore your index and do a Seq Scan because loading index pages is slower than scanning a tiny table in memory.
